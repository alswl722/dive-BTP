# 기능 2. 영업외손익 괴리 배지 (먼저, 쉬움)

## 문제

수기 분석 사례: **본업 적자인데 순익 흑자(일회성 연명)** — 2379(5년 영업적자·순흑자), 695(영업 −467K→순 +831K), 1049 / 반대로 **본업 흑자인데 순손실** — 1878(영업 +228K→순 −216K), 672(영업이익 96%가 영업외에서 증발).

현재 `영업외손익비중 = 순이익률_최근 − 영업이익률_최근`이 [features_finance.py:193](backend/etl/features_finance.py:193)에 이미 계산되고, passthrough로 프론트까지 전달됨([company_view.py:525](backend/etl/company_view.py:525)). **그러나 화면에 숫자만 흐르고 해석은 심사자 몫.** 명시적 위험 신호가 아니다.

## 왜 점수화가 아니라 배지인가

`영업외손익비중`은 비단조(클수록 좋은 것도 나쁜 것도 아님)라 [scoring_finance.py:76](backend/etl/scoring_finance.py:76)에서 이미 의도적으로 점수 제외. 이 판단을 유지한다 — **점수에 섞으면 "본업 부실"과 "일회성 호재"가 상쇄되어 신호가 죽는다.** 대신 `risk-signals.tsx`의 배지로 승격한다(기존 자본잠식·축어긋남과 동일 계층).

## 설계

### 판정 규칙 (프론트 `deriveSignals`에 추가)

영업외손익비중을 그대로 쓰지 않고, **본업 흑자/적자 방향과 조합**해야 의미가 산다. `영업외손익비중`만으로는 "본업 적자를 영업외로 메움"과 "본업 흑자에 영업외 보너스"를 구분 못 한다. 두 원본값이 필요:

| 케이스 | 조건 | 심각도 | 문구 |
|---|---|---|---|
| 일회성 연명 | 영업이익률_최근 < 0 **AND** 순이익률_최근 ≥ 0 | 위험 | 본업 적자를 영업외 이익으로 흑자 전환 — 지속가능성 낮음 |
| 본업 훼손 | 영업이익률_최근 ≥ 0 **AND** 순이익률_최근 < 0 | 주의 | 본업 흑자이나 이자·손상 등으로 최종 적자 |
| 영업외 편중 | 둘 다 흑자 **AND** \|영업외손익비중\| ≥ `nonop_gap_pct`(기본 20) | 정보 | 순이익의 상당부분이 영업외 — 본업 기여 확인 필요 |

- **임계값 `nonop_gap_pct`는 config로**(`composite_score_weights.yaml`에 넣거나 프론트 상수 파일). 단, 케이스1·2는 부호만 보므로 임계값 불필요(견고).
- 심각도는 절대 임계값 최소화 — 방향(부호)이 주 신호.

### 구현 (실제 반영 — 초기 계획에서 2점 정정)

**정정①: 단일연도 → 다년.** 최근연도(2024) 부호만 보면 2379(만성 연명, 최근연도는 둘 다 적자)를 놓친다(실측 확인). → `features_finance.py`에 다년 파생 `영업외의존_연수`(영업<0 & 순≥0 연수) + `재무관측연수` 추가([features_finance.py:221](backend/etl/features_finance.py:221)). `scoring_finance.PASSTHROUGH` → `company_view` passthrough로 전달.

**정정②: `risk-signals.tsx`는 dead code.** 실제 화면 신호 엔진은 `lib/review-summary.ts`(심사 요약). 배지는 여기 `deriveReviewSignals`에 추가.

판정(2케이스):
| 케이스 | 조건 | 심각도 | 데이터원 |
|---|---|---|---|
| 만성 연명 | `영업외의존_연수 ≥ LIFELINE_CHRONIC_YEARS`(2) | 위험 | passthrough(다년) |
| 본업 훼손 | 최근연도 영업이익률 ≥ 0 & 순이익률 < 0 | 주의 | rawMetrics(단발) |

### 검증 (완료)

- ✅ 실측: 2379(연명 4년)=위험 발화, 1878(영업 12%·순 −12%)=주의 발화, 117(연명 1년, 최근연도 정상)=무발화.
- ✅ 브라우저 3케이스 재현, 콘솔 에러 없음. 점수 회귀 0건(`SCORE_COLS` 불변).

### 산출물

- `features_finance.py`(다년 파생 2컬럼) · `scoring_finance.py`(passthrough) · `company_view.py`(전달) · `review-summary.ts`(배지 2 + 상수) · `types/index.ts` · fixture(2필드 주입)
- **DB 마이그레이션·스코어링 SCORE_COLS 변경 없음**

# 기능 1. 고용 회전율 (나중, 파이프라인 작업)

## 문제

수기 분석: **117**(취업·퇴직 ≈0 → 소수정예 안정) vs **695**(2024 가입 98인데 취업 133/퇴직 91 → 회전율 90%대, 가입자수만 보면 성장이나 실상은 대량 입·퇴사). 서류상 "고용 성장"을 회전율로 반박 — 발제 브리핑 "정보 비대칭성" 축에 직결.

## 데이터 현황 (정정)

`pension_subscribers`(가입자) / `pension_employed`(취업=신규취득) / `pension_retired`(퇴직=자격상실)는 **config에 있어 `company_yearly_metrics` 테이블에는 이미 적재됨**([company_yearly_metrics.yaml:8-10](backend/etl/config/company_yearly_metrics.yaml)). 단 **`master_table` 뷰에 투영이 안 돼**([010_views.sql](db/migrations/010_views.sql) 고용 컬럼은 `employee_count`만) `features_finance`가 못 읽는다. → **엑셀 재적재 불필요, 뷰만 확장하면 된다.**

## 핵심 설계 결정: 재무 안정성 축에 넣지 말 것

**회전율을 재무 4축(안정성)에 점수로 섞지 않는다.** 근거:
- 재무 안정성(부채비율·자기자본비율)과 고용 회전율은 **다른 종류의 리스크**. 섞으면 축 의미가 흐려지고, 성장기업의 높은 채용(정상)이 안정성 점수를 부당하게 깎는다.
- 회전율은 **맥락 신호**로 두는 게 맞다 — 점수 한 숫자보다 "가입 98인데 퇴직 91" 같은 원값 노출이 심사자에게 더 유용.

→ **패턴: `자본잠식_플래그`와 동형.** 파생값 계산 → passthrough/원값 전달 → `risk-signals.tsx` 배지 + 스코어카드에 원값 표시. 스코어링 `SCORE_COLS` 미변경.

## 파생 컬럼 설계

연도별(2020~2024) 3개 원값에서:

| 파생 | 산식 | 비고 |
|---|---|---|
| `이직률_최근` | 퇴직자 / 가입자 (최근 공통연도) | `safe_ratio` — 가입자 0/결측 → NaN |
| `채용률_최근` | 취업자 / 가입자 | 성장 맥락 |
| `고용순증_최근` | 취업자 − 퇴직자 | 절대 증감 |
| `회전율_최근` | (취업자 + 퇴직자) / 가입자 | 총 인력 이동. 695 케이스 포착 |
| `고용관측연수` | 3개 값 모두 있는 연도 수 | **결측/0 구분**(흑자관측연수 패턴) |

- 설립연도 이전 연도는 결측이 정상 → `고용관측연수`로 분모 노출. 관측 0년이면 전부 NaN.
- **단위 주의 없음**(전부 인원수, 재무 천원 이슈와 무관).

## 구현 (실제 반영된 것)

1. **뷰 확장** — `db/migrations/010_views.sql`의 `master_table`에 국민연금 3종×5년(15컬럼) 투영. `employee_count`와 동일한 `MAX(CASE WHEN year=...)` 패턴. 컬럼명 `국민연금가입자수_YYYY`/`국민연금취업자수_YYYY`/`국민연금퇴직자수_YYYY`.
   - ✅ **010 직접 수정이 맞다(초기 계획 정정).** `master_table`은 일반 VIEW(`CREATE OR REPLACE VIEW`)라 마이그레이션 재실행 = 즉시 재정의, **적재 불필요**(뷰가 `company_yearly_metrics`를 live로 읽고, 국민연금 데이터는 이미 그 테이블에 적재돼 있음). 별도 마이그레이션은 뷰 정의 이중화만 낳아 더 나쁘다.
2. **파생 계산** — `features_finance.py` `compute_features`에 고용 블록 추가([영업외의존 블록 바로 뒤](backend/etl/features_finance.py:241)). `find_year_cols`를 **직접 호출**(METRIC_HINTS 우회):
   - `이직률_최근` = 퇴직/가입, `고용회전율_최근` = (취업+퇴직)/가입, `고용순증_최근` = 취업−퇴직, `고용관측연수` = 셋 다 존재 & 가입>0 인 연수. 최근 관측연도(`last_valid_index`) 값으로 산출.
   - ✅ **METRIC_HINTS에 넣지 않은 이유**: `validate_scores.py` 게이트 A1이 METRIC_HINTS 전 지표를 fatal 검사한다. 국민연금은 점수축이 아니므로 힌트에 넣으면 안 됨 → `find_year_cols` 직접 호출로 연도 매칭 인프라만 재사용하고 게이트 영향 0.
3. **passthrough 전달** — `scoring_finance.PASSTHROUGH`에 4컬럼 추가([scoring_finance.py:76](backend/etl/scoring_finance.py:76)) → `company_view.py`의 passthrough 블록에서 clean() 전달.
4. **프론트** — `types/index.ts` passthrough 타입 4필드 + `lib/review-summary.ts` `deriveReviewSignals`에 배지. **`risk-signals.tsx`는 dead code라 사용 안 함**(실제 렌더 엔진은 review-summary).

## 판정 규칙 (배지, review-summary.ts)

| 조건 | 심각도 | 문구 |
|---|---|---|
| 이직률_최근 ≥ `TURNOVER_HIGH`(0.5) **또는** 고용회전율_최근 ≥ `CHURN_HIGH`(0.8) | 주의 | 순증 {±n}명이나 이직률 {x}%·회전율 {y}%. 가입자 증가가 실제 성장인지 확인 |

- 두 임계값은 `review-summary.ts` 상단 상수(기존 `STALE_PATENT_YEARS` 등과 동일 관례). 표본 검증: 695(이직률 0.93·회전율 2.29)만 발화, 117(0)·1730(0.19)·1878(0.10)·2379(0.45)는 무발화.
- **sev=주의**(위험 아님): review-summary 철학상 위험은 결격 수준(자본잠식·안정성 하위)만. 성장기업의 정상 채용일 수 있어 "확인 필요".
- ⚠️ 본선에서 국민연금 컬럼명이 다르면 `find_year_cols` fallback(부분일치)이 흡수하나, 스템 불일치 시 파생이 NaN → 배지 미발화(조용한 실패). 뷰 컬럼명을 `국민연금가입자수_YYYY` 규칙으로 유지할 것.

## 검증 (완료)

- ✅ 파생값 실측: 695(이직률 0.93/회전율 2.29/순증 +42), 117(0/0/0), 2379(0.45).
- ✅ 브라우저: 695="고용 회전율 높음 — 순증 +42명이나 이직률 93%·회전율 229%" 발화, 117 무발화, 콘솔 에러 없음.
- ✅ 점수 회귀 0건(HEAD fixture와 4축·종합점수 대조). `SCORE_COLS` 불변.
- ⚠️ **DB 모드 미검증** — 로컬 parquet은 이미 국민연금 컬럼 보유. docker로 마이그레이션 재실행 후 `master_table`에 컬럼 생성·파생 산출 확인 필요.

## 산출물

- `010_views.sql`(뷰 15컬럼) · `features_finance.py`(파생) · `scoring_finance.py`(passthrough) · `company_view.py`(전달) · 프론트(타입+배지) · fixture(4필드 주입)
- **`SCORE_COLS` 불변 → 종합점수 회귀 없음**(설계 핵심)

# 화면 UX (최종 반영)

배지는 `frontend/lib/review-summary.ts`의 `deriveReviewSignals`가 만들고, `review-summary.tsx`가 렌더한다. 3개 배지 모두 sev·문구는 그 파일에.

## 고용 회전율 배지 (`kind: "employment"`)
- **포지션 바(항상)** — 회전율 업종내 백분위(`scoring_finance` CONTEXT_PCT_COLS → `company_view.employment.회전율백분위`). 제목 줄 우측에 컴팩트 배치(전폭 바는 목록 6배지 벽에서 너무 뚱뚱). "전체/업종 상위 N%" + 중앙값 마커 + 이 기업 점.
- **연도별 펼침표** — `employment.series`(국민연금 가입/취업/퇴직) + 연도별 이직률. 만성 vs 일회성을 심사자가 직접 확인(695는 2020년부터 불안정).
- **문구** — 순증(취업−퇴직) 부호로 분기, "순증" 용어 대신 자연어. "최근 1년" 명시(세 지표 다 최근연도 1년치). pos: "채용이 퇴사보다 N명 많지만…실제 성장인지", neg: "퇴사가 채용보다 N명 많고…인력 이탈이 잦습니다".
- **목록 필터** — `company-filters.ts` `employmentRiskOnly` + `isEmploymentUnstable`(배지와 동일 임계). `filter-panel.tsx` "심사 신호 > 고용 불안정". "만 보기"만 제공(제외는 스크리닝 목적에 안 맞음).

## 영업외 연명 배지 (`kind: "lifeline"`)
- **연도별 펼침표** — `nonopIncome.series`(연도별 영업이익·당기순이익, 억원). 본업<0·최종≥0인 해에 "연명" 강조 → "5년 중 4년" 주장을 표로 감사.
- 다년 주장이라 펼침 가치 높음(고용 배지와 동형).

## 본업 흑자·최종 적자 배지
- **펼침 없음(의도)** — 최근 1년 스냅샷이라 다년 감사 가치 낮음. 문장으로만.

## 펼침 추가 원칙
배지가 **시간에 걸친 주장**을 하고 심사자가 그걸 **연도별로 감사**하고 싶을 때만 펼침을 붙인다(고용·연명 ○, 본업훼손 ×). 모든 배지에 달면 심사 요약이 위젯 벽이 되어 신호가 묻힌다.

## 텍스트 줄바꿈
배지 detail `<p>`에 `text-pretty break-keep` — 한글 orphan 방지 + 단어 중간 안 끊김.

## 본선 검증 (도구 완비 — 측정은 본선 당일)
배지 임계값은 큐레이션된 표본 11개에 맞춰졌다. 표본 발화율: 고용회전율 36% · 영업외연명 18% · 본업훼손 18%(전부 표본 특성으로 과대 추정). **본선에서 배지 발화율·데이터 커버리지·지표 분포를 재측정해 임계값을 재조정해야 한다.**

✅ **검증 도구 구현 완료** — `frontend/scripts/validate-badges.ts` (설계: [배지검증_설계노트.md](배지검증_설계노트.md)).
당초 `validate_scores.py`(파이썬)에 섹션을 붙일 계획이었으나 **별도 TS 러너로 변경**했다. 배지 판정 로직이 `review-summary.ts`에만 있어 파이썬으로 복제하면 drift가 생기기 때문 — 실제 `deriveReviewSignals()`를 그대로 실행해야 화면과 100% 일치한다. 임계값 튜닝 워크플로도 그 문서에 있다.

```bash
cd frontend && npx tsx scripts/validate-badges.ts --api http://localhost:8000
```
