# 배지 검증 스크립트 설계노트 (`frontend/scripts/validate-badges.ts`)

## 문제

심사 요약 배지(현재 18종 — 단일 출처는 `review-summary.ts`의 `deriveReviewSignals`, 배지 추가/삭제 시 이 숫자는 자연히 어긋나므로 정확한 목록은 그 함수를 볼 것)의 임계값은 **큐레이션된 표본 11개**에 맞춰졌다. 본선(~1,200개)에선 다르게 나온다 — 너무 자주 뜨면(위험>20% / 주의>30%) 심사자가 무시, 안 뜨면(0%) 무의미. 본선 당일 발화율·커버리지·임계 민감도를 재측정해 임계값을 재조정한다. `validate_scores.py`(축 점수)와 같은 철학, 대상만 배지.

## 핵심 결정: 판정 로직을 재구현하지 않는다 (TS 러너)

배지 발화율을 세려면 데이터(쉬움: API) + **판정 로직**이 필요한데, 판정 로직은 `review-summary.ts`(+ `concurrent-support.ts`·`duplicate-risk.ts` ~200줄)의 TS에만 있다. 파이썬으로 복제하면:
- 임계값 아닌 로직(동시수행 기간겹침·"연도 같아야 비교" 등)이 바뀌면 조용히 틀림
- 새 배지 추가 시 놓침
- **본선 당일 믿을 수 없는 검증기** = 없느니만 못함

→ 재구현 대신 **실제 `deriveReviewSignals()`를 그대로 실행**한다. 화면 배지와 100% 일치, drift 0, 새 배지 자동 반영. 대가는 Node/TS 스크립트라는 것과 API 기동 필요(어차피 화면 보려면 떠 있음).

### 왜 파이썬 validate_scores와 도구가 갈리나
- `validate_scores.py`(축 점수): 입력이 `features_score` 하나 → 파이썬으로 충분.
- 배지: 입력이 재무+tech+LLM+중복 전부 조립된 Company 객체 + TS 판정 로직 → TS로 실제 코드를 돌리는 게 유일하게 정확.

## 실행

```bash
cd frontend
npx tsx scripts/validate-badges.ts                    # API(localhost:8000)
npx tsx scripts/validate-badges.ts --api http://host:8000
npx tsx scripts/validate-badges.ts --fixtures         # 커밋된 fixture(표본 11개, 스모크)
```
- `tsx`는 `@/` 별칭을 tsconfig에서 해결(devDep 불필요, npx가 캐시).
- 읽기 전용. `/companies` GET만. `/companies`는 인증 없음(권한 제한은 프론트 화면 게이팅이지 API 인증 아님).
- **`--api`(DB 모드)가 fixtures보다 완전** — LLM 배지(사업목적 무관 등)는 DB에만 있어 fixtures엔 안 뜬다.

## 출력

- **[A] 배지별 발화율** — 실제 deriveReviewSignals 집계, 심각도순. 위험>20%·주의>30% ⚠️. 동적 제목(결측 N건 등)은 숫자→N 정규화로 묶음.
- **[B] 데이터 커버리지** — 배지가 뜰 수 있는 모집단(고용관측연수≥1 등). <70% ⚠️(소수만 대상).
- **[C] 임계 민감도** — 숫자 임계 배지의 발화율을 임계값별로. **현재값(`*`)은 review-summary.ts/scoring.ts 실제 상수에서 import** → stale 없음.
- **요약** — ⚠️ 목록 + '재무 안정성 하위 구조적 25%' 정책 이슈 표기.

## 임계값 튜닝 워크플로 (본선)

1. `[C]`에서 임계값별 발화율을 **바꾸기 전에** 확인(예: 이직률 0.6이면 몇 %).
2. `review-summary.ts`의 상수 한 줄 수정(예: `TURNOVER_HIGH = 0.5 → 0.6`).
3. 이 한 줄이 **화면 배지 + 검증 스크립트 둘 다** 반영(스크립트가 그 파일을 그대로 돌림). `[C]`의 `*`·"현재 X"도 자동으로 따라옴.

→ 공유 config 파일을 따로 두지 않은 이유: TS 러너라 애초에 drift가 없고, 상수를 import하므로 단일 출처가 `review-summary.ts`로 유지됨. (`LOW_PERCENTILE`만 검증용으로 `export` 추가 — 동작 무변경.)

## 검증 (스크립트 자체)

- fixtures 스모크 → 수기 측정치 재현(고용 36%·연명 18%·훼손 18%) = 화면 로직과 일치 확증.
- API 모드 → LLM 배지까지 집계됨 확인.
- tsc 통과, 읽기 전용(git status 깨끗).

## 표본에서 이미 보인 것 (본선 재확인 대상)
- 반복 수혜 100%·동시수행 45%/36% — 표본이 반복선정 큐레이션이라 과대. 본선 정상화 여부가 관건.
- 축 어긋남 64% — 백분위 분산. 본선에서도 높으면 `AXIS_MISALIGNMENT_THRESHOLD` 상향.
- 재무 안정성 하위 — 백분위<25라 **구조적으로 ~25%가 "위험"**. sev(위험) 정책 이슈(팀 논의).

## 후속
- 나머지(R&D·중복·LLM) 배지도 이미 [A]에 다 집계됨. 임계 민감도([C])만 재무 위주 → 필요시 R&D 임계(특허 소멸률·정체년수) 추가.
- 원한다면 임계값을 config로 추출 가능(현재는 불필요 — 상수 import로 단일 출처 유지).
