# 기업지원사업 도메인 노트 (발제사 Q&A)

> 부산테크노파크(BTP) 담당자에게 받은 질의응답 정리. 발제 문제정의·데이터 해석의 근거자료.
> 관련 문서: 프로젝트 배경은 `CLAUDE.md`, 재무/기술 축 설계는 `docs/재무축_설계노트.md`·`docs/기술축_설계노트.md`

---

## 1. 기업지원사업 진행 절차

```
사업공고 → 기업신청 → 서류검토 → 대면평가 → 현장실태조사 → 선정/통보 → 사업수행 → 최종평가 → 사업비 지급
```

- 대부분의 사업이 이 순서를 따르지만, **사업에 따라 일부 단계가 생략**되기도 함(예: 대면평가나 현장실태조사 없이 서류검토만으로 선정).
- 우리 도구가 다루는 시점은 **"서류검토~선정/통보" 구간** — 즉 담당자가 신청기업을 평가·선정하는 단계. 사업수행 이후(정산, 최종평가)는 스코프 밖.

## 2. 사업공고의 선정기준

- 공고문에는 모집 대상 기업의 기준이 제시되며, **매출·고용이 기본 기준**으로 거의 항상 포함됨.
- 사업 성격에 따라 추가 기준이 붙는 경우가 있음(업종 제한, 인증 보유 여부 등 — 사업마다 다름).
- 기준을 넘는 기업들이 신청서(사업계획서)를 제출하고, 그 사업계획서로 평가가 이루어지는 구조.

## 3. 사업계획서 = 평가 기준

- 실제 평가는 기업이 제출한 **사업계획서**(재무정보 + 기업현황/개요/연혁 등 기재)를 바탕으로 이루어짐.
- **사업계획서 양식은 사업마다 다름** — 들어가는 항목이 공고별로 차이가 있어 표준 양식이 없음.
  - 양식 확인 경로: 부산테크노파크 홈페이지 → 공고/안내 → 사업공고 → 각 공고문 첨부파일
- 현재 구조: 정량 지표(매출/고용/연구개발비/영업이익 등) + 사업계획서 정성 내용만으로 평가 → **그 외 정보(특허, NTIS, 법인등기부등본 사업목적 등)를 반영한 종합적 기업정보 뷰가 없다는 것이 발제사의 문제의식**.
  - → 우리 프로젝트의 "종합 스코어카드"가 정확히 이 공백을 겨냥함(`CLAUDE.md`의 S-tier 기능 참고).

## 4. 제공 데이터 관련

- **실제(발제) 데이터는 샘플데이터와 동일한 형태·항목** — 컬럼 구조는 그대로, **양(row 수)만 더 많음**.
  - → ETL 설계 시 컬럼 매핑을 하드코딩하지 말라는 `CLAUDE.md` 개발원칙 3번("ETL은 설정파일 기반")과 일치. 실제 데이터 투입 시 스키마 변경 없이 양만 늘어날 것으로 가정 가능.
- **기업명·사업자등록번호는 비식별화되어 기업일련번호로 대체 제공**. 실명·사업자번호 매칭은 발제 데이터 범위에서 불가능(엔티티 매칭 로드맵 항목과 연결).

## 5. 중복지원 확인 — 금지사항 아님, 오히려 권장

- 하나의 기업이 여러 사업에 중복 지원/중복 수혜를 받았는지 확인하는 것은 **금지사항이 아니며**, 오히려 TP의 고유 목적(지역 내 우수기업 발굴·지원)과 맞닿아 있음.
- **Why**: TP의 역할이 "우수기업 발굴"인 이상, 특정 기업에 지원이 쏠리는 현상(반복 선정)을 파악하는 것 자체가 업무적으로 유효한 요구. 억제해야 할 부정행위로만 볼 필요는 없고, 형평성/편중도 모니터링 관점으로 접근 가능.
- **How to apply**: 중복지원 탐지 기능(`CLAUDE.md` S-tier)의 프레이밍을 "부정 탐지"보다 "편중도·형평성 모니터링" 쪽에 가깝게 잡아도 됨. 반복 선정 자체가 문제라기보다, 그 정보를 담당자가 볼 수 있는 도구가 없다는 것이 문제.

## 6. 심사결과 기능

- 심사결과(합격/불합격 판정) 자체를 보여주는 기능은 **필수 아님**.
- 다만 필요하다고 판단되면 제시해도 무방 — 발제사가 막는 항목은 아님.
- → 스코프 확정 시 우선순위 낮게 둘 것. 시간 부족하면 제외해도 감점 요인 아님.

## 요약: 프로젝트 방향에 대한 시사점

| 질문 | 답변 핵심 | 프로젝트 반영 |
|---|---|---|
| 평가는 어떻게 이루어지나 | 정량지표 + 사업계획서(정성)만으로 평가, 특허/NTIS/등기부 등 미반영 | 종합 스코어카드가 채워야 할 공백 확인 |
| 사업계획서 양식은 하나인가 | 사업마다 다름, 표준 없음 | ETL 컬럼 매핑을 하드코딩하면 안 되는 이유가 하나 더 늘어남 |
| 데이터 양/형태 변화 | 형태·항목 동일, 양만 증가 | 스키마 변경 대응 불필요, 스케일(성능) 대응은 필요 |
| 중복지원 확인, 문제 없나 | 금지 아님, TP 목적과 부합 | 편중도/형평성 모니터링으로 프레이밍 |
| 심사결과 기능 필요한가 | 필수 아님, 선택 | 우선순위 낮게 |
