# 지역적합 축 설계노트 (부산 9대 지역전략산업 매칭)

> 관련 코드: `backend/etl/domain_tech.py` (`regional_fit()`), `backend/etl/config/external/busan_strategic_industry.yaml`
> 팀 상호 참고용 — 담당자 미배정 축이라 기존 기술축(팀원B) 파이프라인(`domain_tech.py`)에 얹었다.

출처: 부산광역시 제6차 전략산업 육성 마스터 플랜.pdf

---

## 1. 개요

BTP 심사 브리핑의 **정보 비대칭** 문제 중, 재무·기술력만으론 못 잡는 **"이 기업이 부산이 전략적으로 미는 산업에 속하는가"**를 KSIC 코드로 판정한다. 발굴/지원 우선순위 판단에 직접 쓰이는 정책적 신호다.

- **소스**: 부산광역시 제6차 전략산업 육성 마스터 플랜(별첨1) — 9대 전략산업(디지털테크·에너지테크·바이오헬스·미래모빌리티·융합부품소재·라이프스타일·해양·금융·문화관광) × KSIC 11차 세세분류코드 362개(고유) + 공통코드.
- **조인**: `companies.ksic_code`(11차, 예 `C29299`)와 **정확히 일치**하는지 exact match. 업종그룹(중분류 3자리) 백분위를 쓰는 재무축과 달리, 여기는 **세세분류(5자리) 단위 정확매칭**이 필요해서 별도 로직(`regional_fit`)으로 분리했다.
- **기존 12대 국가전략기술(`national_strategic_tech.yaml`)과 다른 점**: 그건 NTIS 표준분류 텍스트 키워드매칭(전국단위 기술분야), 이건 KSIC 코드 정확매칭(부산 지역단위 산업분류) — 소스도 매칭방식도 다르다. 둘 다 `domain_tech.build()`에서 같이 산출되지만 서로 독립.

## 2. 왜 원본 재추출 과정이 길었나 (데이터 신뢰성 방어 기록)

이 야멜파일 만들기까지 세 번의 시도가 있었다. 기록을 남기는 이유: **스캔 PDF는 사람이든 OCR이든 눈으로 옮기면 반드시 오류가 난다**는 걸 실증했기 때문 — 향후 비슷한 자료를 받을 때 같은 함정에 빠지지 않기 위함이다.

|           |                                                                                                     |                                                                           |
| --------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 3차(채택) | **원본 마스터플랜 PDF**(스캔 아님, 네이티브 텍스트 레이어) 확보 → `pdftotext -layout` + 정규식 파싱 | 9개 산업**전부** footer 선언값과 파싱값 100% 일치, 총합계 362 == 362 확인 |

**결론**: 스캔본·OCR본은 "그럴듯해 보여도" 검증 없이 쓰면 안 된다. 원본(텍스트 레이어 있는 파일)을 구하는 게 결국 가장 빠른 길이었다.

## 3. KSIC 알파벳 접두 정규화 (부수적 검증)

원본 표의 코드는 5자리 숫자만(`26329`)이라 `companies.ksic_code` 포맷(`C26329`)과 안 맞았다. 대분류(알파벳) 구간은 임의 규칙이 아니라 **KSIC 11차 분류체계 자체가 고정한 값**이라, 국세청 「업종코드-11차 표준산업분류 연계표」(2023년 귀속, 실측 1,786건)를 직접 받아 대분류별 min/max를 실측 집계해 검증했다(예: C=10~34, D=35단독, J=58~63 등). 이후 이 표를 자동 적용해 362+56건 전부 대분류 매핑 실패 0건 확인 후 접두를 붙였다 — 수기 오타 위험 없음.

## 4. 매칭 로직 (`regional_fit`)

```
companies.ksic_code
    → unique(고유) 코드와 먼저 대조 → 매칭되면 (산업명, "고유") 반환 — 강한 신호
    → 없으면 common(공통) 코드와 대조 → 매칭되면 (산업명, "공통") 반환 — 약한 신호
    → 둘 다 없으면 (None, None)
```

- **고유 우선**: 공통코드(연구개발업·측정업 등)는 여러 산업에 동시에 걸려있어, 단독 매칭만으로 "이 산업 소속"이라 단정하면 과대판정이다. `tech_intensity()`(기존 기술수준등급 함수)와 동일하게 예외/우선순위 체계를 그대로 재사용.
- **미매칭 = 결측 아님**: `지역전략산업_부합=False`는 "전략산업이 아니라는 사실"이지 데이터 부족이 아니다. NaN과 구분해서 항상 False로 명시(CLAUDE.md 원칙 "결측을 0으로 오인 금지"와 같은 취지 — 여기서는 반대로 "사실인 False를 결측처럼 흐리지 않기").
- **NTIS 유무 무관**: 축8/기존 도메인 판정과 달리 KSIC만 있으면 전 기업에 적용 — NTIS 과제가 없는 기업도 지역적합 판정은 받는다.

## 5. 검증 (샘플 + 합성 테스트)

- 실 샘플 11개: 9곳 매칭(전부 고유), 2곳 미매칭. `python3 domain_tech.py`로 재현 가능.
- `test_tech_edge_cases.py`에 5개 회귀테스트 추가 — 합성 기업 C1(KSIC `C29199`)→융합부품소재, C2(`C21309`)→바이오헬스, C4(`C31114`)→미래모빌리티, C5(`J58221`)→디지털테크, C3(`C25113`, 9대 산업 코드에 없음)→미부합(False, NaN 아님) 전부 통과.

## 5-1. 조인 소스 신뢰성 검증 — `companies.ksic_code` vs `support_records.업종코드` (2026-07-25, 본선 데이터)

`eda_ksic_consistency.py`가 본선 데이터(기업 2,886개)에서 두 소스의 KSIC 일치율 **20.5%**,
BTP 쪽에서 행마다 다른 코드를 쓰는 기업 **827개(34%)** 를 보고했다. `regional_fit()`이
`companies.ksic_code`만 조인키로 쓰는 게 이 결과로 봤을 때도 안전한 선택인지 확인이 필요해
원본 xlsx(`scripts/kodata.xlsx`, `scripts/btp.xlsx`)를 직접 열어 대조했다.

**원인 — 조인 오류·버전차이가 아니라 BTP `업종코드`가 "회사"가 아니라 "그 신청 건"의 자체신고 값.**
기업 702는 KODATA `J63999`(정보서비스업) 고정인데, BTP 안에서만도 연도·사업별로 `C58221`,
`63999`, `20423`(화장품), `58221`, `J63999`, `242403`(화장품뷰티페스티벌) 등 **7종 이상**을
썼다 — 정보서비스 회사가 "화장품뷰티산업사업화지원사업"에도 지원하면 그 건은 화장품 코드로
찍히는 식. 같은 기업이 BTP 자체 내에서도 코드가 안 고정되므로(가설 ②: 9/10/11차 버전 차이라면
기업당 코드가 고정돼야 함 → 기각), 조인 키가 잘못 매칭됐을 가능성(가설 ③)도 기업 5곳을 직접
대조해 배제했다(company_id 일치, 사업명·주생산품이 기업별로 논리적으로 일관 — 뒤섞인 흔적 없음).

**결론 — 이 축은 영향 없음.** `regional_fit()`은 설계 시점부터 `support_records.업종코드`를
전혀 안 쓰고 `companies.ksic_code`(KODATA, 기업당 고정 1값)만 조인키로 썼다(§1 참고,
`009_industry_code_map.sql`도 이미 같은 이유로 이 컬럼을 "참고용"이라 경고해뒀었다). 이번
실측이 그 설계 결정을 재확인해준 것 — 별도 대응 불필요.

**참고 — 20.5%는 과소평가일 수 있음**: 스크립트가 기업당 첫 1건만 비교하는데, 702 사례처럼
여러 건 중 일부는 실제로 일치한다. "기업당 하나라도 일치하는 행이 있는가" 기준으로 재계산하면
체감 일치율이 더 높게 나올 수 있음 — EDA 스크립트 개선 여지로 팀에 공유.

## 6. 한계 & 다음 단계

- **시점 캐비엇**: 이 표는 2025년 확정 "제6차"(2026년 시행분) 기준. BTP 지원기록(2022~2024년)에 소급 적용하는 것이라, 해당 기간 실제 적용 버전과 다를 수 있음 — 본선에서 필요시 주최측 확인 권장(yaml 파일 헤더에도 명시).
- **고유/공통 가중치 미정**: 지금은 매칭유형(고유/공통)만 태깅하고 스코어 가중치 차등은 아직 안 넣음. 종합점수에 "지역적합" 그룹으로 편입할 때 고유=강한가점·공통=약한가점으로 반영 필요(범위 밖, 다음 단계).
- **종합점수 미편입**: `composite_score_weights.yaml`에 아직 그룹 추가 안 함 — 다른 축(재무/기술/정합성) 가중치 재분배가 필요한 팀 합의 사항이라 이번 작업 범위에서 제외.
