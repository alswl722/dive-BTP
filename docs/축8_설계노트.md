## 1. 개요

BTP 심사 브리핑의 **정보 비대칭** 중 특히 "담당자가 제출 서류(사업목적서)만으로 지원사업과의 정합성 판단"의 한계를 해소한다. 등기부등본 사업목적 텍스트(최대 10줄) vs 실제 받은 지원사업의 **의미 정합성**을 LLM(Claude)이 판정해 스코어카드에 편입한다.

- **스코어카드 편입**: 축8은 기업 역량의 한 축(정체성·전문성)이라 스코어에 **포함**
- **축9와 역할 분리**: 축9(BTP 지원이력 flagging)는 반복지원 이상탐지 → 역량 스코어 **제외**의 별도 flag 축
- **접근 원칙**(CLAUDE.md 원칙1 규칙기반 우선): 규칙 매트릭스 → 판정불가시 LLM. 전량 LLM 호출 아님
- **스코어카드 삽입 지점**: `company_view.py:138`이 `_mock: ["businessFit"]`로 필드 예약 상태 — 축8이 이 목업을 실데이터로 교체하는 위치

핵심 원칙: **규칙기반 1단 필터로 LLM 호출 최소화**, **미통과=이상 아님(판단유보)**, **임계값 하드코딩 없음**(본선 재산정), **컬럼 매핑 config화**(원칙3).

## 2. 데이터 특성 → 대응 결정 (왜 이렇게 방어했나)

EDA(사업목적 105행·11개 기업 · 지원이력 92건 · 사업목록 757행)에서 확인된 특성마다 대응을 설계에 반영했다.

| 데이터 특성 / 이슈 | 왜 문제인가 | 우리 대응 |
| --- | --- | --- |
| **어휘 겹침 극단적으로 낮음** — 사업목적 vs 지원사업명 jaccard 평균 0.005, 전 11개 기업 0~0.026, 7/11 완전 0 | 단순 키워드 매칭(BM25·TF-IDF)로 정합성 못 잡음. 정상 지원도 겹침 0이라 규칙만으로는 오탐 다수 | **LLM 시맨틱 판정 필수**. 문자열 매칭은 후보군에서 제외, LLM 필요성의 정량적 근거로 사용 |
| **사업목적 형식성**("~제조업, ~판매업, 및 이에 부수되는") vs **지원사업 구체성**("스마트공장 구축") | 어휘 스타일이 원천적으로 겹칠 수 없음 | 사업목적은 **의미 임베딩·LLM 해석 대상**, 지원사업은 카테고리(business_type / support_detail_main)와 텍스트(program_name / description) 둘 다 활용 |
| **KSIC 대분류 3종만 관측**(C 제조업·J 정보통신·Q 보건복지) × business_type 7종 = 21셀 중 7셀 0 | 화이트리스트가 sparse. "미관측=이상"으로 판정하면 정상 조합 오탐 | **positive whitelist만** 사용. 미통과 = "판단유보 → LLM 호출" 대상. **미통과 ≠ 부정합** (코드 주석·설계문 명시) |
| **가장 흔한 조합 C+패키지지원 32건**(전체 92건 중 34.8%) | 그 자체는 정상이지만 매트릭스 편중 → 소수 조합 신뢰도 낮음 | 통과 조합은 신뢰, 소수 조합은 LLM 재확인 방향으로 임계 설정 |
| **business_type 7종·support_detail_main 19종·조합 30쌍** | 카테고리 다양 → 규칙 매트릭스가 큰 쪽으로 확장 | 원본 축은 business_type(7종, 저차원), 세부는 LLM 프롬프트에 보조 컨텍스트로만 |
| **Whitelist 자기참조 편향** — whitelist가 관측 92건에서 파생되므로 관측 조합은 100% 자동 통과. 관측 1~2건 조합도 "확정"이 되어 통계적 근거 부족 | 샘플 데이터에서 LLM이 절대 호출되지 않음(데모·발표 불가), 소량 관측은 우연 가능성 있음 | **신뢰도 tier 판정 도입** — `axis8_thresholds.yaml`로 `high(≥10)/medium(≥3)/low(<3)` 분리. `accept_confidence: [high, medium]`만 whitelist 통과. `low`는 관측 있어도 **판단유보 → LLM 재확인** 대상. 결과: 실 92건 중 8건(8.7%) LLM 호출 → 데모 작동성·편향 방어 동시 달성 |
| **샘플 11개 편향**(전원 반복선정 큐레이션) | whitelist·임계값 절대 확정 불가 | 로직·구조만 확정, **본선 재산정 명시** — whitelist·tier 임계값 둘 다 config 파라미터화 |
| **Claude API 결제 미승인** | 실 호출 불가 | Phase 3에서 프롬프트·structured output·캐싱·비용 시뮬만 문서화. 실행은 결제 후 |

## 3. 규칙기반 1단 필터 (whitelist, Phase 2에서 구현)

**목적**: LLM 호출을 최소화. "확실히 정상" 조합은 whitelist 통과 → LLM 스킵.

- **whitelist 정의**: `(KSIC 대분류, business_type)` 조합 — EDA 관측 + `사업구분참조` 시트의 사업유형 계층으로 확장
- **신뢰도 tier** (`axis8_thresholds.yaml`, 자기참조 편향 방어):
  - `high` (관측 ≥10건) → 규칙 통과
  - `medium` (관측 3~9건) → 규칙 통과
  - `low` (관측 1~2건) → **판단유보 → LLM 재확인** (우연 관측 방어)
- **판정 로직**:
  - whitelist 통과 & 신뢰도 accept → `businessFit = 100`
  - whitelist 통과 & 신뢰도 low → **판단유보** (LLM 대상)
  - 미통과 → **판단유보** (LLM 대상)
- **금지**: 미통과·low를 "부정합"으로 자동 처리 (샘플 sparse함, 오탐 위험)
- **산출 경로 (Phase 2 완료)**:
  - `backend/app/config/axis8_whitelist.csv` — 관측 기반 (build 스크립트로 재생성)
  - `backend/app/config/axis8_thresholds.yaml` — tier·accept_confidence 파라미터
  - `backend/app/services/axis8.py` — `classify_alignment()` 판정 함수
- **실 데이터 검증(샘플 92건)**: 통과 84건(91.3%), 판단유보 8건(8.7%) → LLM 호출 비율 = 8.7%. Phase 3 비용 시뮬 근거

## 4. LLM 인터페이스 (Phase 3에서 확정)

Claude API 실 호출은 결제 대기. 인터페이스는 결제와 무관하게 지금 확정 가능.

- **structured output 스키마**:
  ```json
  {
    "score": 0-100,
    "match_type": "직접일치 | 간접관련 | 무관",
    "matched_keywords": ["..."],
    "reasoning": "한 문장"
  }
  ```
- **`matched_keywords` 근거 노출**: 담당자 화면 표시 · "왜 이 점수인가" 질문 대응 · 발표 신뢰도 확보
- **캐싱 전략**: `(사업목적 텍스트 해시, program_code)` 키. 사업목적은 기업당 고정이라 재호출 시 히트율 매우 높음 — 비용 절감의 핵심
- **호출 대상**: whitelist 미통과 조합만
- **비용 시뮬 (Phase 3 산출물)**: 본선 기업 수 × 미통과 예상 비율 × 토큰 × 최신 Claude 단가 → 팀 결제 승인 근거자료

## 6. 스코어카드 편입 방식

- **현재 스키마 상태**: `Company._mock: ["businessFit"]`로 필드 예약 (`company_view.py:138`). 필드명·삽입 위치 팀 합의된 상태
- **Phase 5 결정** (`docs/api_응답_스키마.md` §3): **독립 필드 `Company.businessFit: BusinessFit`** 채택 (Axis literal 확장 X). 근거: 축8은 LLM 판정 산출이라 백분위 개념 없음 → 재무 백분위 축 컬렉션과 컨셉 다름
- **`BusinessFit` shape**: `{score, match_type, matched_keywords, reasoning, source}` — `source`로 판정 경로(`whitelist`/`llm`/`pending`) 노출
- **신규 상세 엔드포인트**: `GET /companies/{id}/alignment` — 지원사업별 개별 판정 리스트 (스코어카드 상세 화면 근거 표시용)
- **`_mock` 처리**: whitelist 통과분은 활성화 즉시 `_mock` 제거 / LLM 대상은 결제 대기 중엔 `source: "pending"` + `_mock: ["businessFit.llm"]`로 부분 목업 (투명성)
- **프론트 소스오브트루스**: `frontend/types/index.ts` — 스키마 변경 시 프론트 타입 동시 수정 필요
