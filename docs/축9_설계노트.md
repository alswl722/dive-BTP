# 축9 BTP 지원이력 flagging 설계노트

> 담당: 팀원 D (형우, 기술리드) — 축8·축9 + API 통합
> 관련 코드: `backend/etl/company_view.py:build_rankings`(건수/금액 랭킹 이미 존재 → flag 레이어만 추가), `backend/app/routers/rankings.py`, EDA는 프로젝트 밖 `eda/` 폴더에서 검증

---

## 1. 개요

BTP 심사 브리핑의 **반복지원·중복성 검증 한계**를 해소하는 이상탐지 축. "여러 번 지원받았는데 성과 없음" 기업을 flag하고, "여러 번 받았지만 성장했다"는 정상 반복은 정탐 제외한다.

- **역량 스코어 미포함**: 지원을 많이 받은 게 우수 기업은 아님 → 스코어카드 축 아님
- **별도 flag 축**: 대시보드·랭킹 위에 얹는 이상 신호. `/rankings`(이미 존재) 위에 flag 필드만 추가
- **축1(성장성) 결과 의존**: 성장률은 민지 산출 대기. 현재 mock 인터페이스로 판정 로직 골격만 확정
- **rankings 재구현 금지**: `build_rankings`가 이미 `byCount`/`byAmount` 반환 → 그 위에 flag 레이어만

핵심 원칙: **건수·금액·연속성 3축 분리**(단일지표 flag 금지), **임계값 하드코딩 없음**(config 파라미터·본선 재산정), **성장률 재계산 금지**(민지 산출 소비만).

| --- | --- | --- |

| **성장률 결측·음수·CAGR 불가**(재무축 방어 필요) | 축9가 성장률 직접 계산하면 재무축 방어로직 중복 + 오류 위험 | **민지 축1 산출물 소비만** — 인터페이스 계약: 팀 컨벤션(한글)에 맞춰 `{기업일련번호, 성장성점수, 매출_CAGR?, 매출_증가액?}` DataFrame. 재계산 X. 자세히는 `docs/성장률_인터페이스.md` |

| **rankings 이미 구현**(`byCount`/`byAmount`) | 재구현 시 로직 중복·불일치 위험 | **원칙 준수** — 축9는 `RankingRow`에 flag 필드만 추가, 랭킹 정렬 로직은 그대로 |
| **샘플 편향**(11개 전원 반복선정 큐레이션) | 세그먼트 분포가 일반 신청 모집단과 다름 | 세그먼트 정의는 확정, 각 세그먼트의 실제 비율은 본선 데이터 기준으로 재보고 |

## 4. flag 판정 truth table

**성장률은 민지 축1 산출 대기 → 현재 mock 함수로 골격만**.

| 지원 규모 | 성장률 | 판정 | 발표 라벨 | flag 필드 값 |
| --- | --- | --- | --- | --- |
| 반복 (상위) | 하락/정체 | 🔴 **진짜 flag** | "지원 반복 · 성과 정체" | `"flag"` |
| 반복 (상위) | 성장 | 🟢 **정탐 제외** | "지원 효과 확인" | `"cleared"` |
| 단발 (하위) | 하락 | ⚪ 관측만 | flag 아님 | `"observe"` |
| 단발 (하위) | 성장 | 🟢 정상 | — | `null` |

**교차 로직 (Phase 4 구현 완료)**: `backend/app/services/axis9.py:classify_flag()`

```python
def classify_flag(metrics_row, metrics_df, signal, config) -> FlagClassification:
    is_repeat = _is_repeat(metrics_row, metrics_df, config)  # repeat_metrics OR
    growth = _growth_state(signal, config)                    # None → "unknown"
    # truth table 그대로
    if growth == "unknown":                       status = "unknown"
    elif is_repeat and growth == "stagnant":      status = "flag"
    elif is_repeat and growth == "growing":       status = "cleared"
    elif not is_repeat and growth == "stagnant":  status = "observe"
    else:                                         status = "normal"
```
- **임계값 전부 config** (`axis9_thresholds.yaml`): `growth_score_stagnant`(default 30.0), `support_count_percentile`(75), `total_amount_percentile`(75)
- **`growth_signal`은 민지 산출 소비만** — 계약 문서 `docs/성장률_인터페이스.md`
- **percentile은 매 호출 시 넘어온 metrics_df에서 실시간 산출** (하드코딩 절대값 없음, 표본 편향 방어)
- **`unknown` 상태**: 민지 산출 대기 중 안전 fallback — 발표·화면에 "성장률 미제공" 표시

## 6-1. 패키지지원 세부품목 = 1건 선정 (카운트 정정, 2026-07-24)

### 발견
2024년 `B1_1_3`(지역기업성장사다리지원사업)에 **같은 기업·같은 선정일**로 3행이 있었다 —
기업 1878이 `시제품제작(20,000)` + `컨설팅(5,000)` + `특허지원(2,000)`. 확인 결과
**세부품목별로 기업을 다르게 뽑는 게 아니라, 선정된 한 기업에 여러 품목을 묶어 지원**하는
구조였다(사업유형 자체가 `패키지지원`, `지원구분(주요지원 외 *패키지지원만)` 컬럼이 그 전제).

### 문제 — 반복선정 과대계상
`support_records`를 **행 단위로 세면** 한 사업 1회 선정이 3건으로 잡힌다. 샘플 실측:

| 기업 | 행 수 | 실제 선정 사업 수 | 부풀림 |
| --- | --- | --- | --- |
| 2080 | 10 | 6 | +4 |
| 1786 | 21 | 18 | +3 |
| 2379 · 616 · 672 · **1878** | 8 · 7 · 5 · **3** | 6 · 5 · 3 · **1** | +2 |

전체 74개 (기업×사업) 조합 중 **15건(20%)이 다행 패키지**. 패키지지원 전용 현상도 아니다
(기술지원 `E2_1_6`에서 2080이 4행). 이 상태로는 1878이 "3번 수혜"로 flag되지만 실제로는
**1개 사업 1회 선정** — 담당자가 즉시 반박 가능한 false positive다.

### 정정 — "선정 단위" = (연도, 사업코드)
- `support_count` = **DISTINCT (year, program_code)** — 반복·중복 판정의 유일한 기준
- `item_count` = 행 수(지원 항목수) — 표시·근거용으로 병기(항목 자체는 숨기지 않는다)
- 총지원금은 **행 합산 유지**(패키지 총액이 실제 수령액이므로 정상)
- 사업코드 없는 행은 합칠 근거가 없어 각각 별건 처리(임의 병합 금지)

### 반영 지점
| 위치 | 변경 |
| --- | --- |
| `db/migrations/010_views.sql` | `선정건수`(= `COUNT(DISTINCT (year, program_code))`) 컬럼 추가 |
| `app/services/axis9.py:compute_support_metrics` | `support_count`를 선정 단위 nunique로, `item_count` 신설 |
| `etl/company_view.py:_selection_count` | **원장에서 직접 계산** — 뷰 컬럼 의존 X |
| `etl/company_view.py:build_rankings` | `byCount` 정렬 기준을 선정건수로, `항목수` 병기 |
| `frontend/lib/duplicate-risk.ts` | `recentSelectionCount`·`selectionsByYear`가 선정 단위로 집계 |

**뷰 컬럼에 의존하지 않는 이유**: parquet 모드의 `master_table.parquet`은 DB 뷰의 스냅샷이라
뷰를 고쳐도 재덤프 전까지 컬럼이 없다 → 뷰 값에 의존하면 그동안 **조용히 옛 값(행 수)** 이 나간다.
원장에서 세면 parquet·DB 어느 경로든 같은 값이 나온다(프론트도 `supportHistory`에서 동일 기준으로 계산).

`concurrent-support.ts`는 이미 `같은 사업의 분할 행`을 제외하고 있어 영향 없음(확인 완료).

### 검증
- 합성 대조: 패키지 3행(1878) → `support_count=1`·`item_count=3`, 진짜 3개 사업 수혜 → `3`·`3`. 금액은 27,000 합산 유지.
- fixture 재생성 결과가 원본 엑셀 실측 부풀림(2080 +4, 1786 +3, 1878 +2 …)과 **정확히 일치**.
- 랭킹 순위 실제 변동: 2080 10건→6건, 1878 3건→1건.

### 화면(중복수혜 탭) — 목록도 사업 단위로
카운트만 고치고 목록이 행 나열이면 "1건 선정"이라 써놓고 아래엔 3줄이 보이는 모순이 생긴다.
`groupBySelection()`(`lib/duplicate-risk.ts`)으로 **사업 단위로 묶고 세부품목을 그 안에 접어** 넣었다.

```
2024-05-24  지역기업성장사다리지원사업   27,000천원  [선정]
            패키지지원 · 세부품목 3개
              - 시제품제작   20,000천원
              - 컨설팅        5,000천원
              - 특허지원      2,000천원
```

- 그룹 키에 **결과(선정/탈락/포기)를 포함** — 같은 사업에서 일부 품목만 탈락한 경우를 한 덩어리로
  합치면 선정건과 탈락건이 뒤섞인다(2080: 같은 사업이 선정·탈락 두 그룹).
- 세부품목 목록은 **2개 이상일 때만** 펼침(1개면 그룹 금액과 같은 값이 반복될 뿐).
- 카드 "총 지원건수"는 `groups.length`(목록과 같은 기준)를 쓴다. `support.선정건수`는 **선정만**
  세는 값(반복선정 랭킹용)이라 탈락·포기까지 포함하는 이 목록의 헤더로 쓰면 또 어긋난다.

### 부수 발견 ① `선정건수`가 탈락까지 세고 있었음
`_selection_count`·뷰 컬럼 모두 결과를 안 가리고 DISTINCT를 셌다 — "반복**선정**"을 세는 값에
탈락이 섞이는 건 명백한 오류. 축9(`compute_support_metrics` 호출 전 `지원대상` 필터)와 같은
기준으로 맞췄다(뷰는 `FILTER (WHERE selection_result = '지원대상')`).

### 부수 발견 ② 날짜 결측 행은 타임라인에서 빠진다
선정일·시작일이 **둘 다 없는 행**은 타임라인에 위치를 못 잡아 `support_history()`가 제외한다
(원본 결측 그대로, 임의 날짜 대체 안 함). 그런데 선정건수·총지원금에는 포함되므로 목록과 숫자가
어긋나 보인다. 샘플에서 3곳(1786·1178·672) 발생하고, **1178의 누락 건은 176,000천원**으로
그 기업 총액의 절반에 가깝다 — 목록만 보고 "이게 전부"라 판단하면 최대 건을 통째로 놓친다.
→ 숨기지 않고 목록 위에 경고 문구로 표기(`ConcurrentPanel`의 `missingPeriod` 표기와 같은 방침).
