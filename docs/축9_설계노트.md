# 축9 BTP 지원이력 flagging 설계노트

> 담당: 팀원 D (형우, 기술리드) — 축8·축9 + API 통합
> 관련 코드: `backend/etl/company_view.py:build_rankings`(건수/금액 랭킹 이미 존재 → flag 레이어만 추가), `backend/app/routers/rankings.py`, EDA는 프로젝트 밖 `eda/` 폴더에서 검증

---

## 1. 개요

BTP 심사 브리핑의 **반복지원·중복성 검증 한계**를 해소하는 이상탐지 축. "여러 번 지원받았는데 성과 없음" 기업을 flag하고, "여러 번 받았지만 성장했다"는 정상 반복은 정탐 제외한다.

- **역량 스코어 미포함**: 지원을 많이 받은 게 우수 기업은 아님 → 스코어카드 축 아님
- **별도 flag 축**: 대시보드·랭킹 위에 얹는 이상 신호. `/rankings`(이미 존재) 위에 flag 필드만 추가
- **축1(성장성) 결과 의존**: 성장률은 민지 산출 대기. 현재 mock 인터페이스로 판정 로직 골격만 확정
- **rankings 재구현 금지**: `build_rankings`가 이미 `byCount`/`byAmount` 반환 → 그 위에 flag 레이어만

핵심 원칙: **건수·금액·연속성 3축 분리**(단일지표 flag 금지), **임계값 하드코딩 없음**(config 파라미터·본선 재산정), **성장률 재계산 금지**(민지 산출 소비만).

## 2. 데이터 특성 → 대응 결정 (왜 이렇게 방어했나)

| 데이터 특성 / 이슈 | 왜 문제인가 | 우리 대응 |
| --- | --- | --- |
| **"건수 ≠ 금액"** — 1786: 21건/166,960천원 (소액다건) vs 1178: 8건/360,700천원 (대형소수, 금액 1위) | 단일 지표(건수 또는 금액)로 flag 걸면 정상 케이스 오탐. 기획서 3.3 핵심 발견 | **3축 분리**: 건수·금액·연속성 각각 percentile로 판정 후 세그먼트 교차 |
| **전 기업 3년 연속수혜** (median = max = 3, 전원 2022~2024) | 샘플에서 연속성 지표 변별력 없음(전원 동일값) | 연속성 지표 로직·구조는 확정, 임계값은 **본선 재산정** — config 파라미터 |

| **성장률 결측·음수·CAGR 불가**(재무축 방어 필요) | 축9가 성장률 직접 계산하면 재무축 방어로직 중복 + 오류 위험 | **민지 축1 산출물 소비만** — 인터페이스 계약: `{company_id, growth_score, revenue_cagr, revenue_delta}` DataFrame. 재계산 X |
| **percentile 절대값 편향** — 지원건수 P50=8, P75=9.5, P90=10 (일반 신청기업 대비 이례적으로 높음) | 임계값 확정하면 본선에서 대부분 미달·초과 편중 | 임계값은 **P75/P90 상대 기준** + config로 노출. 본선 데이터에서 재산정 원칙 명시 |
| **rankings 이미 구현**(`byCount`/`byAmount`) | 재구현 시 로직 중복·불일치 위험 | **원칙 준수** — 축9는 `RankingRow`에 flag 필드만 추가, 랭킹 정렬 로직은 그대로 |
| **샘플 편향**(11개 전원 반복선정 큐레이션) | 세그먼트 분포가 일반 신청 모집단과 다름 | 세그먼트 정의는 확정, 각 세그먼트의 실제 비율은 본선 데이터 기준으로 재보고 |

## 4. flag 판정 truth table

**성장률은 민지 축1 산출 대기 → 현재 mock 함수로 골격만**.

| 지원 규모 | 성장률 | 판정 | 발표 라벨 | flag 필드 값 |
| --- | --- | --- | --- | --- |
| 반복 (상위) | 하락/정체 | 🔴 **진짜 flag** | "지원 반복 · 성과 정체" | `"flag"` |
| 반복 (상위) | 성장 | 🟢 **정탐 제외** | "지원 효과 확인" | `"cleared"` |
| 단발 (하위) | 하락 | ⚪ 관측만 | flag 아님 | `"observe"` |
| 단발 (하위) | 성장 | 🟢 정상 | — | `null` |

**교차 로직 (Phase 4 구현 완료)**: `backend/app/services/axis9.py:classify_flag()`

```python
def classify_flag(metrics_row, metrics_df, signal, config) -> FlagClassification:
    is_repeat = _is_repeat(metrics_row, metrics_df, config)  # repeat_metrics OR
    growth = _growth_state(signal, config)                    # None → "unknown"
    # truth table 그대로
    if growth == "unknown":                       status = "unknown"
    elif is_repeat and growth == "stagnant":      status = "flag"
    elif is_repeat and growth == "growing":       status = "cleared"
    elif not is_repeat and growth == "stagnant":  status = "observe"
    else:                                         status = "normal"
```
- **임계값 전부 config** (`axis9_thresholds.yaml`): `growth_score_stagnant`(default 30.0), `support_count_percentile`(75), `total_amount_percentile`(75)
- **`growth_signal`은 민지 산출 소비만** — 계약 문서 `docs/성장률_인터페이스.md`
- **percentile은 매 호출 시 넘어온 metrics_df에서 실시간 산출** (하드코딩 절대값 없음, 표본 편향 방어)
- **`unknown` 상태**: 민지 산출 대기 중 안전 fallback — 발표·화면에 "성장률 미제공" 표시

## 5. 발표 하이라이트 사례 (BTP 심사 담당자에게 왜 유용한가)

### 사례 1 — 1786 (소액다건, "여러 부서 반복선정" 실증)
- **21건 · 총 166,960천원 · 사업유형 5종 · 세부구분 9종**
- 발제 브리핑 원문 "부서별 심사가 분절적으로 이루어져 특정 기업의 중복 지원을 즉각 파악하기 어려움"의 **정량 증거**
- 이 기업은 다양성 지표에서 max=5로 튀는 outlier — 대시보드 배지 후보

### 사례 2 — 1178 (대형소수, 대비군)
- **8건 · 총 360,700천원(금액 1위) · 유형 4종**
- "건수 ≠ 금액" 실증 — 단일 지표 flag의 오탐 위험 사례
- 1786(건수 1위)과 1178(금액 1위) 나란히 보여주면 3축 분리 필요성이 한눈에

### 사례 3 — 지원×매출증가액 사분면 (flag 교차로직 실제 결과)
EDA `06_support_vs_growth.png`의 4분면 판정 (매출 2020→2024 raw diff, 민지 CAGR 붙으면 교체):

| 위치 | 기업 | 판정 |
| --- | --- | --- |
| 우하단 (대형지원+정체) | **117, 1878** | 🔴 flag 후보 |
| 우상단 (대형지원+성장) | **1178, 1730, 672** | 🟢 정탐 제외 |

**핵심 메시지**: 우하단·우상단 기업은 "지원 많이 받았다"는 raw 사실은 같지만 판정은 정반대. → **flag는 단순 반복 카운트가 아닌 교차 판정**이라는 발표 서사.

## 6. rankings 위 flag 레이어 (Phase 5 API 상세 예정)

- **Phase 5 결정** (`docs/api_응답_스키마.md` §4): 3개 편입 지점 확정
  1. **`RankingRow`에 `flag`·`segment` 필드 추가** — 랭킹 화면 인라인 배지
  2. **`Company.duplicateFlag: DuplicateFlag | None`** — 스코어카드 상세 배지 (스코어에는 미편입, 별도 필드)
  3. **신규 엔드포인트 `GET /flags/duplicate-support`** — 관리자 대시보드 필터·정렬 조회
- **`DuplicateFlag` shape**: `{status, label, is_repeat, growth_state, segment, is_high_diversity}` — 발표 근거·화면 배지 재료
- **성장률 mock 상태 처리**: `status: "unknown"` + `_mock: ["duplicateFlag.growth"]` (투명성), 민지 산출 붙으면 자동 실데이터
- **`build_rankings` 재사용**: 로직 재구현 X, flag_df·segment_df 결과를 row에 부착만

## 7. 한계 & 다음 단계

- **축1 성장률 대기**: 인터페이스 계약 초안 확정 (`docs/성장률_인터페이스.md`) · 민지 합의 후 mock 교체. `axis9.growth_signals_from_axis1(df)` 헬퍼가 계약 위반 시 즉시 raise
- **연속수혜 지표 변별력**: 샘플에서 전원 3년 → 본선 데이터에서 실효성 재검증
- **계열사 우회 지원 탐지**: 금융위원회 기업기본정보 API로 계열사 구조 확보 시 가능. **본선 데이터에 법인등록번호 살아있을 때만 유효** — 기획서 로드맵
- **이상탐지(Isolation Forest) 조건부 적용**: 본선 표본 N에 따른 분기
  - N ≥ 100: 규칙 위에 IF 얹어 잔여 이상 신호 탐색 (SK 대회 경험 재활용)
  - N < 30: 규칙기반 유지
  - 30 ≤ N < 100: 규칙만, IF 로드맵으로 발표
- **본선 당일**:
  - 3축 percentile 재산정
  - `GROWTH_THRESHOLD`·`COUNT_THRESHOLD`·`AMOUNT_THRESHOLD` config 값 데이터 driven 확정
  - 각 세그먼트 실 비율 재산출 후 발표자료 사례 교체
